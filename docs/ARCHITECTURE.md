# 아키텍처

## 계층 구조

소스는 `src/memory_typing` 아래의 다음 계층으로 분리한다.

- `domain`: 책, 장, 문장, 퀴즈, 학습 세션 같은 순수 데이터 모델과 도메인 개념을 정의한다.
  PySide6와 데이터베이스 구현에 의존하지 않는다.
- `core`: 타이핑 평가, 점수 계산, 학습 이벤트, 퀴즈 채점 및 복습 정책을 담당한다.
  UI 없이 단위 테스트할 수 있어야 한다.
- `storage`: SQLite 연결, 명시적인 스키마 변경, 저장소 구현을 담당한다. 다른 계층에 SQLite
  세부 구현이 새지 않도록 한다.
- `ui`: PySide6 창과 위젯을 담당한다. 사용자 입력을 core에 전달하고 결과를 표시하며,
  실질적인 학습 규칙을 자체적으로 구현하지 않는다.

의존성은 UI와 storage가 domain/core의 인터페이스와 모델을 사용하는 방향으로 유지한다.
core는 PySide6에 의존하지 않는다.

## 텍스트 모델

다음 세 값은 서로 다른 개념이며 절대로 혼용하지 않는다.

- `original_text`: 가져온 정본 원문이다. 학습 이벤트 표시를 만들기 위해 변경하거나 파괴하지
  않는다.
- `display_text`: 현재 학습자에게 보이는 문자열이다. 빈칸, 힌트, 초성 또는 숨김 효과가
  적용될 수 있다.
- `typed_text`: 학습자가 입력하고 IME가 확정한 문자열이다.

정답 평가는 최종적으로 `original_text` 또는 이벤트가 명시한 정답 사양을 기준으로 한다.
한국어 입력은 물리 키 이벤트가 아니라 Qt의 표준 텍스트 편집 및 확정 입력을 기준으로 처리한다.

## 학습 이벤트 생명주기

학습 이벤트는 `core.study_events`의 순수 Python 추상화이며 PySide6나 저장소에 의존하지 않는다.
각 `StudyEvent` 구현은 다음 생명주기를 따른다.

1. `EventContext`로 안정 ID가 있는 현재 문장, 선택적인 이전 문장, 시도 번호를 받는다.
2. `is_eligible()`로 해당 문맥에서 이벤트를 실행할 수 있는지 판단한다.
3. `prepare()`가 원문과 별개인 `EventPresentation.display_text`와 안내 문구를 만든다.
4. UI는 IME에서 확정된 입력을 `EventAnswer.typed_text`로 전달한다.
5. `evaluate()`가 원문 또는 이벤트의 명시적 정답 사양과 답안을 비교하여 `EventResult`를 반환한다.

`EventEngine`은 등록된 이벤트 중 적격 이벤트만 고르고, 준비된 이벤트와 문맥을
`PreparedEvent`로 묶은 뒤 답안을 해당 이벤트로 다시 전달한다. 이벤트 종류는 안정적인
`event_type`으로 식별하며 중복 등록하지 않는다. 적격 이벤트가 없으면 준비 결과는 `None`이다.

`original_text`, `display_text`, `typed_text`는 생명주기 전체에서 별도 값으로 유지한다. 이벤트는
표시를 변환하더라도 불변 `Sentence.original_text`를 변경하지 않으며, 평가는 정본 원문 또는
이벤트가 명시한 정답을 기준으로 한다.

타이핑 입력은 Qt 문서에 확정된 문자열을 기준으로 평가한다. 단, 문장 끝의 한글이 계속 preedit로
남아 불필요한 스페이스나 Enter를 요구하지 않도록, 확정 문자열의 현재 커서 위치에 preedit를
삽입한 읽기 전용 후보가 원문과 정확히 일치하는 경우에만 Qt 입력기에 조합 확정을 요청한다.
후보가 부분 입력이거나 원문과 다르면 조합 상태를 그대로 유지하며 직접 자모 키를 해석하지 않는다.

엔진에는 `RandomSource`를 직접 주입하거나 시드를 지정할 수 있다. 이벤트 선택과 향후 이벤트
내부의 무작위 표시 생성은 같은 난수원을 사용하므로 테스트에서 선택과 표시를 재현할 수 있다.
현재는 구조를 검증하기 위한 `ExactMatchEvent` 하나만 제공하며 실제 빈칸·회상 이벤트는 이 계약을
구현해 독립적으로 추가한다.

## 확장 방향

SQLite 스키마 변경은 버전이 명확한 마이그레이션으로 관리하고 안정적인 콘텐츠 ID를 사용한다.

## 로컬 영속성

`storage.Database`는 SQLite 파일과 연결의 수명주기를 담당한다. 새 데이터베이스 파일은 최초
연결 시 현재 스키마 버전으로 순차 초기화되며, 모든 연결에서 `PRAGMA foreign_keys = ON`을
적용한다. 스키마 버전은 SQLite의 `user_version`으로 기록한다. 현재 버전은 2이며 버전 1의
콘텐츠 데이터는 학습 기록 테이블을 추가하는 명시적 마이그레이션 후 그대로 유지된다.

`storage.BookRepository`는 `Book → Chapter → Paragraph → Sentence` 계층을 SQL 행으로
매핑한다. 계층 전체 삽입은 하나의 트랜잭션이므로 중간 오류가 발생하면 전부 롤백된다. 조회는
각 부모 안에서 `source_order`로 명시적으로 정렬하며 저장된 안정 ID와 `original_text`를 그대로
도메인 객체로 복원한다. 도메인 모델은 SQLite나 SQL을 알지 못한다.

`storage.StudyRepository`는 장 단위 `StudySession`과 문장 단위 `SentenceAttempt`를 저장한다.
UI는 `core`에 정의된 저장소 프로토콜에만 의존하고 `MainWindow`가 SQLite 구현을 주입한다.
한 장의 첫 확정 입력에서 세션을 시작하고, 문장 완료 시 `TypingEngine`이 만든 평가 상태를
문장 시도로 저장하며, 마지막 문장 완료 시 세션 완료 시간을 기록한다. 세션과 시도는 콘텐츠의
안정 ID를 외래 키로 참조하므로 목록 인덱스에 의존하지 않는다.

콘텐츠 외래 키는 `ON DELETE RESTRICT`와 `ON UPDATE RESTRICT`를 사용한다. 따라서 자식이 있는
부모의 삭제나 ID 변경이 암묵적으로 연쇄 실행되지 않는다. 향후 콘텐츠 편집 및 학습 이력 기능도
명시적인 저장소 작업과 마이그레이션으로 추가하며, 콘텐츠 변경의 부작용으로 학습 이력을 삭제하지
않는다.
